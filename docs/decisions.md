# 技术决策记录

## D-001 Python 环境：conda 环境 `jsc`，Python 3.11，conda-forge 频道（2026-10-24）

**背景**：项目需要独立的 Python 环境（第一阶段只有 `export_anki.py` 一个脚本，第二阶段会加入语音识别等依赖）。

**可选方案**
- Python 版本：3.10 / 3.11 / 3.12+
- 频道：Anaconda 默认频道（`defaults`）/ conda-forge

**选择**：Python 3.11 + conda-forge。

**原因**
- 3.11 比 3.10 快，且主流的语音/ML 库（第二阶段可能用到的 faster-whisper、PyTorch 等）对 3.11 的支持最成熟；3.12+ 部分库的 Windows 预编译包仍可能滞后。
- Anaconda 默认频道现在要求先接受服务条款（ToS）才能用，且对组织有商用授权限制；conda-forge 是社区维护、无此限制，包也更新更快。创建命令：
  `conda create -n jsc python=3.11 -c conda-forge --override-channels`

## D-002 Skill 输出格式：固定模板 + 单一推荐 + 内联注音（2026-10-24）

**背景**：Skill 的核心价值是在真实对话中帮用户「听懂、接上」。用户此时往往只有几秒钟看屏幕；同时第一阶段的完成标准要求 20 句测试句「格式全部稳定」，后续脚本（Anki 导出）和第二阶段的字幕 App 也要解析输出。

**可选方案**
- 自由回答 vs 固定模板
- 给三条平行建议让用户自己挑 vs 标出一条推荐
- 注音：HTML `<ruby>` / Anki 格式 `漢字[かんじ]` / 内联括号 `漢字(かんじ)`
- 解释在前（先讲语法再给回复）vs 可说的内容在前

**选择**
1. 回复建议模式使用固定模板：「听懂（原文/意思/要点）→ 回复建议（丁寧/カジュアル/かんたん）→ 生词」，标题固定，模板外不加开场白和结尾语。
2. 三条回复中恰好一条标 ⭐，并附一句推荐理由。判断顺序：用户说明的对象 > 对方的用语礼貌程度 > 默认丁寧。
3. かんたん 定位为「保底回答」：1 句、N4 以内词汇语法，而不是第三种语体。丁寧/カジュアル 尽量以反问结尾，把话题抛回给对方。
4. 需要用户个人事实的部分用【】标出，不编造。
5. 所有汉字词用半角括号内联注音 `漢字(かんじ)`，重复出现的词也注。
6. 复盘的生词卡用列名固定的 CSV 代码块（`front,reading,meaning,example`）。

**原因**
- **信息按紧急程度排序**：对话中的用户最需要「能马上说出口的一句话」，所以「听懂」压缩到三行，语法细节只留 1 条，生词放最后。看完回复建议就可以停。
- **单一推荐降低决策成本**：在对话中让用户从三个选项里挑，等于把最难的「该用哪种礼貌程度」又丢回给用户。⭐ 替用户做决定，另外两条留作学习。默认丁寧，是因为说得太礼貌的代价远小于失礼。
- **保底回答**：「接不上」很多时候是紧张导致的大脑空白，此时需要的是最短、最不会错的一句话。反问结尾则解决「答完一句话就冷场」的问题。
- **不编造**：模型不知道用户的真实经历，直接编一个答案，用户可能照念一句不真实的话；【】把「需要替换」变成显式信号。
- **内联括号注音**：口语工具的用户要照着念，所以全部注音。括号格式在终端、聊天窗口、Markdown 中都能正常显示（`<ruby>` 依赖 HTML 渲染，Anki 格式要求汉字前加空格，在聊天中可读性差），且可以用正则无损转换成其他格式。
- **固定格式 = 可测试 + 可解析**：标题固定、恰好一个 ⭐ 等约束可以写成自动检查；Skill 中附完整示例作为 few-shot，比纯文字规则更能稳定格式；Anki 导出脚本只需找到 CSV 代码块，Skill 与脚本之间的接口由此固定。

**代价 / 风险**
- 全部注音让文字变长，N2 水平的用户可能觉得啰嗦。若试用反馈如此，可以加「注音级别」开关。
- 固定模板会让简单寒暄（如「おはよう」）的回答显得过重；暂时接受，以稳定性优先。

## D-003 推荐（⭐）判断：分步规则 + 口语标记，而不是「对方用什么就回什么」（2026-10-24）

**背景**：⭐ 推荐是 Skill 最核心的判断，也最容易「凭感觉」。需要一套可复现、能用测试集检验的规则（`skill/references/politeness.md`）。

**可选方案**
1. 完全交给模型自由判断
2. 镜像原则：对方用です/ます就回丁寧，用普通体就回カジュアル
3. 分步规则：用户指定 > 对象表 > 丁寧标记 > 普通体 + 口语标记 > 默认丁寧

**选择**：方案 3。

**原因**
- **方案 1 不可测**：同一句话多次运行可能推荐不同结果，无法满足「格式稳定」的完成标准，也说不清错在哪。
- **方案 2 有两个漏洞**：
  - **上下关系不对称**：上司、先輩对你用普通体很正常，你镜像回去就是失礼。所以用户说明对象时，对象表优先于对方用语。
  - **普通体不等于朋友**：「大丈夫？」这类短句谁都可能说。只有出现口语标记（マジ、〜じゃん、〜てる 等）时才推断为朋友语境，否则视为「判断不了」。
- **默认丁寧**：两种错误的代价不对称——对朋友太礼貌只是显得生分，对上司太随便是失礼。在不确定时选代价小的一边。
- **规则写进 reference 而不是 SKILL.md**：SKILL.md 只保留 5 步摘要，详细标记清单按需读取（Skill 的渐进式加载），避免主提示词过长。
- **可检验**：测试集每句都标了预期 ⭐，并刻意包含边界句（如第 20 句「大丈夫？」应得丁寧），用来检查模型是否遵守规则。

## D-004 根据第 1 轮测试修订输出规则（2026-10-24）

**背景**：第 1 轮 20 句测试（`tests/results_2026-10-24.md`）中，结构和 ⭐ 推荐全部稳定，但清单只过了 14/20。失败集中在几条规则上。

**修订与原因**
| 问题（出现句） | 判断 | 修订 |
|---|---|---|
| かんたん 超过 1 句（5 句） | 模型反复写「感叹 + 一句」（ありがとう！うれしい。），这本身很自然，是规则过严，不是模型错 | 改为「最多 2 个短句、约 15 个假名以内、比丁寧明显更短」——限制的目的是「短」，用字数比句数更贴切 |
| かんたん 与丁寧相同（#20） | 违背「保底」的定位 | 明确要求必须比丁寧更短更简单 |
| 原文被改写（#15 加字、#19 直接写成纠正后的文字） | 规则没说原文要逐字，属于规则歧义；改原文会让学生以为对方就是这么说的 | 原文逐字照抄，只加注音；推测的正确说法只写在「要点」里 |
| 注音错误「一(いち)か月」（#7）、注音形式颠倒「ひま(暇)」（#12） | 逐字注音会丢失促音等读音变化 | 有读音变化的词整词注音，并给出示例；读音必须写在汉字后面 |
| 丁寧/カジュアル 写成 3 句、推荐理由列多个备选（#10–#12、#15、#20） | 模型想把「拒绝时怎么说」等备选塞进回复 | 计句方式写明（。！？）；备选统一放推荐理由，且最多一个 |

**方法上的取舍**：失败时先区分「模型没遵守规则」和「规则本身不合理/有歧义」。前者加强规则或示例，后者改规则。かんたん 句数属于后者，所以选择放宽规则而不是加重措辞。

**第 2 次修订（第 2 轮测试后）**
| 问题 | 修订 |
|---|---|
| カジュアル 仍写成 3 句（#15）：模型爱在末尾加一句体贴话 | 加入 ✗/✓ 对照示例，说明体贴话要么并进前一句、要么删掉；加「输出前自检」，要求逐条数「。」「！」「？」 |
| 推荐理由附 2 个备选（#16）：模型不把「若你们不熟就改用丁寧」当作备选 | 明确禁止语体切换提醒（三条回复本身已覆盖不同语体），备选只留一个具体的日语说法 |
| 推荐理由出现「（第 3 步）」（#7）：照抄了 politeness.md 示例里的步骤标注 | 示例去掉行内标注，对应关系挪到示例上方说明；明确禁止输出步骤编号、章节号、文件名 |

**教训**：给模型看的示例会被原样模仿，连注释也会被照抄。示例里只放希望出现在输出里的内容；同理，正例不要用测试集里的原句，否则测试会高估效果。

## D-005 测试方法加入日语审查：独立的更强模型盲审 + 人工抽查（2026-10-24）

**背景**：v3 整体回归格式 19/20，但人工通读发现了格式清单测不到的日语错误（语法不通、角色颠倒）。学生会照着说出口，日语错误比格式错误严重得多。

**可选方案**
1. 只靠人工通读
2. 让生成模型输出前自检
3. 另开上下文，用更强的模型按固定提示词审查（LLM-as-judge），人工抽查校准

**选择**：方案 3，并保留方案 2（SKILL.md 的自检）作为第一道防线。

**原因**
- **人工不可靠也不可扩展**：校准时发现，人工判定的 3 个问题里有 1 个是误判（#15），而且漏掉了 #16 的立场矛盾。作者本人日语不是母语，单靠人工既慢又不稳定。
- **自检不够**：同一个模型在同一次生成里检查自己，容易重复同样的盲点。
- **独立 + 更强**：审查员与生成模型分开上下文（看不到生成时的推理），并使用更强的模型（生成 Sonnet、审查 Opus）；盲审，不读测试记录，避免被人工结论带偏。
- **先校准再使用**：用人工已标注的第 4 轮输出检验审查员——2/2 找到真实问题、没有附和人工误判、额外发现 1 个硬性问题，才把它纳入测试流程。
- **分级判定**：语法/角色/立场/语体/读音为硬性（必须为 0），不自然为软性（只记录），拿不准的标「存疑」交给人工。避免审查员为了凑数报告问题，也避免把风格偏好当成错误。

**同时修订的规则（SKILL.md v4）**：站在学生的角色说话（不说对方角色的固定用语）；请求句型不要拼接（✗〜てお願いします）；三条回复立场**和行动**一致；「无」用简体。新规则的例子刻意避开测试集原句（吸取 D-004 的教训）。

**局限**：审查员也是模型，可能和生成模型有共同的盲点；人工抽查（尤其是日语母语者）仍然是最终依据，计划在第一阶段的朋友试用中补上。

## D-006 对上司/老师/店员时 カジュアル 照样给出，但加 ⚠ 提示（2026-10-24）

**背景**：日语审查员在 #3 #4 #6 #10 反复标出同一类存疑——对象明确是店员、上司、老师时，カジュアル 一条若被学生照说会失礼。这是 D-002「三条永远都给、用 ⭐ 推荐」的副作用。

**可选方案**
1. 维持现状，只靠 ⭐ 推荐引导
2. 对象不适合时不给 カジュアル，换成另一种丁寧说法
3. カジュアル 照样给，在对象明确不适合时加 ⚠ 提示

**选择**：方案 3（作者决定）。

**原因**
- **保留学习价值**：同一句话的普通体说法本身就是学习材料，学生以后对朋友说同样的话时能用上；去掉就少了这部分。
- **格式稳定**：三条永远是 丁寧 / カジュアル / かんたん，格式和解析脚本都不用分情况处理（方案 2 会让第二条的含义随场景变化）。
- **⭐ 不够**：⭐ 只说明「哪条最好」，不说明「哪条会出事」。学生在紧张时可能随手挑一条，需要一个明确的禁止信号。
- **⚠ 放在中文行而不是日语行**：学生会照着日语那一行念，提示写进去可能被一起念出来，也会污染将来要解析的日语字段。

**边界**
- 「对象明确」只认两种依据：学生说明，或原文是店员服务用语。只凭对方用了敬语不加——用敬语的人不一定是上级（D-003 第 5 步的「判断不了」情况）。
- 先只覆盖作者指定的三类（上司、老师、店员）。客户、面试官、先輩等是否也加，留待试用反馈。
- SKILL.md 中举的店员用语例子刻意避开测试集原句。

## D-007 情景库：任务型「节点 + 变化」而不是完整台词脚本（2026-10-24）

**背景**：第一阶段完成标准要求「至少 6 个情景能完整走完一轮陪练」。需要决定 `skill/references/scenarios.md` 里每个情景写到多细。

**可选方案**
1. 完整台词脚本：每句台词都写好，模型照着念
2. 只给一句场景描述，其余交给模型发挥
3. 结构化卡片：固定开场白 + 流程节点 + 变化 + 完成条件 + 听力难点 + 常见失礼

**选择**：方案 3，共 8 个情景（N4×2、N3×4、N2×2）。

**原因**
- **方案 1 太死**：学生的回答千变万化，脚本无法回应偏离的回答；而且同一场景练第二次就变成背台词。
- **方案 2 不可测**：每次走向都不同，无法判断「完整走完一轮」，也无法比较改动前后的效果。
- **方案 3 兼顾两者**：
  - **固定开场白**：同一场景的开头一致，便于测试和对比。
  - **流程节点**：规定「要谈到什么」而不是「怎么说」，模型可以自然回应学生，又不会跑题。
  - **变化**：每次随机加入一个，重复练习时内容有差异；「简单模式」可关掉。
  - **完成条件**：给「完整走完」一个可判定的终点，同时防止对话无限延长。
  - **听力难点 / 常见失礼**：前者让角色有意识地说出学生该听懂的说法，后者把 💡 的触发条件具体化（只在误解或明显失礼时提示，和 A 模式的 politeness.md 对齐）。
- **语体写进每张卡片**：「你对学生」和「学生应使用」分开写，例如 S4 先輩会夹普通体、学生仍须用です/ます，把 D-003 的「上下关系不对称」放进练习里。
- **8 个而不是 6 个**：完成标准是「至少 6 个」，多准备 2 个作为余量，某个情景测试中走不通时不影响达标。场景选择以在日留学生/求职者的高频场景为主，S8 求职面试同时贴合作者自己的使用场景。

**同时决定**：陪练时角色台词不附中文翻译——听懂本身是练习目标；学生卡住时再按 A 模式给翻译和回复建议。

## D-008 情景陪练规则修订 + ⚠ 范围扩大（2026-10-24）

**背景**：8 个情景的首轮模拟测试（`tests/roleplay_2026-10-24.md`）中，8/8 能走到最后节点、💡 预埋错误 8/8 命中，但只有 2/8 在 8 轮内收尾，S1、S7 到上限都没结束；💡 有 4/8 用日语写；「每轮一句」没有定义。

**修订**
| 问题 | 原因判断 | 修订 |
|---|---|---|
| 不收尾（S1 节点走完后还追问小票、筷子） | 规则只写「达到完成条件时结束」，没写节点走完要主动收尾；S1 的完成条件依赖教练自己说出「ありがとうございました」 | 节点走完或达到完成条件时，**这一轮台词就是收尾台词**；第 7 轮起主动推进，第 8 轮必须收尾；「变化」占用节点、不增加轮数；S1/S7 完成条件改写成教练自己的动作 |
| 轮数怎么数不清楚 | 求助那条算不算一轮没定义 | 只数角色台词，求助不计 |
| 求助后在同一条消息里续台词（S5） | 规则没禁止 | 求助那条消息到此为止 |
| 💡 用日语 | 模板写的是「中文简短提示」，但没有示例，模型按角色语言写了 | 明确「解释一律中文，只有更好的说法用日语」并给示例 |
| 一轮说 3 句 | 「一句」有歧义（和 A 模式 D-004 同一个问题） | 一轮 = 一次发言，≤ 2 句，≤ 1 个问题 |
| 开场有的加中文说明有的不加 | 未规定 | 统一为「第一行中文说明场景和角色，第二行开场白」——对学习者定位场景有帮助 |

**⚠ 范围扩大（偏离 D-006 时作者指定的三类）**：从「上司/老师/店员」扩大到「上司/老师/客户/面试官/店员等服务人员」。
- 原因：测试中 S8 面试官、S7 中介都出现了需要 ⚠ 的情况；`politeness.md` 的对象表本来就把客户、面试官和上司、老师归为同一类（必须丁寧），只给其中一部分加 ⚠ 不一致。
- 先輩没有加入：先輩是否能说普通体因职场而异（D-003 也只要求「默认丁寧」），加 ⚠ 会过度。
- 这是在作者授权「自行推进」后做的决定；如果作者坚持三类，把 SKILL.md「カジュアル 的 ⚠ 提示」一节的列表改回即可。

**复盘规格补充**：生词卡 `example` 不加注音、片假名词 `reading` 与 `front` 相同、纠错不收只差标点的细节——来自 3 份真实复盘输出中出现的不一致。

## D-009 工具链：标准库脚本 + 自动格式检查 + 打包脚本（2026-10-24）

**选择**

## D-010 来自真实使用的两处修订：分级注音 + 个人信息先查后占位（2026-10-24）

**背景**：作者第一次在 Claude.ai 里实际使用（输入「我想用日语做自我介绍」），发现两个问题：

| 注音过多 | ①维持全部注音 ②完全交给模型判断「难词」 ③用一份确定的基础汉字表划线，并提供级别切换 | **③**。②不可测、每次标准不一；③把「难不难」变成可查的规则：词中汉字全在 N5–N4 表（`references/basic_kanji.md`，245 字）且是常用读法 → 不注；特殊读法（今日、一人…）列为例外必注。学生可说「全部注音 / 少注音 / 不要注音」切换。同一份表也被 `check_format.py` 用来自动检查漏注，规则和测试共用一个数据源。 |
| 个人信息 | ①维持只占位 ②直接问学生 ③先查对话/记忆/过往对话，查到就用并注明来源，查不到才占位 | **③**。用户期望的就是「工具记得我」；注明来源让学生能核对；查不到时仍不编造，并明确禁止写「像真的」假名字。 |

**这也是一个 NLP 方向的起点**：基础汉字表是确定性的语言资源。下一步计划用形态素分析（SudachiPy/MeCab）做词级判断和读音校验，替代现在按「字」判断的近似——这同时服务于两个目标：读音更准（自用）和体现 NLP 技术（作品集）。

**背景**：作者判断 Skill 形态不能满足真实需求（要在对话/视频进行中看字幕，而不是事后粘贴文字），改为先做本地应用。第一个原型：麦克风或系统音频 → 实时日语识别 → 带假名的字幕。新增 `app/jsc_live/`（应用代码）和 `app/requirements.txt`，和 `skill/` 并列，不改动原有目录。

| 环节 | 可选方案 | 选择与原因 |
|---|---|---|
| 识别模型 | ①OpenAI Whisper large-v3 ②kotoba-whisper（large-v3 用日语语料 ReazonSpeech 蒸馏）③ReazonSpeech k2/sherpa-onnx ④云端 API | **②**，用 faster-whisper（CTranslate2）跑 `kotoba-whisper-v2.0-faster`。日语准确率接近 large-v3，解码器只有 2 层，速度快很多；本机 8 GB 显卡 float16 足够；本地运行不需要 API Key、不上传音频。③更快但生态和标点不如 Whisper；④有延迟和费用。 |
| 推理引擎 | ①transformers ②faster-whisper | **②**：同样模型显存更小、更快，pip 装 CUDA 运行库即可，不用装完整 CUDA Toolkit。Windows 下需把 `site-packages/nvidia/*/bin` 加进 DLL 搜索路径（`cuda_setup.py`）。 |
| 音频采集 | ①sounddevice/PyAudio ②soundcard | **②**：一个库同时支持麦克风和 WASAPI 回采（录「电脑正在播放的声音」），后者是看视频/网课/通话字幕的关键。 |

| 实时性 | ①whisper_streaming 的 LocalAgreement（滑动窗口反复识别，提交两次一致的前缀）②按句识别 + 说话中每 0.8 秒出一次临时结果 | **②**：实现简单，一句话说完后只等停顿判定（0.6 s）+ 识别（约 0.25 s）。临时结果用 beam=1 换速度，最终结果 beam=5。①在长句里更平滑，先不做。 |
| 注音 | ①按字查字典 ②pykakasi ③MeCab（fugashi）+ UniDic | **③**：形态素分析按**词**给出上下文读音（今日→きょう、一人→ひとり、大人→おとな），按字查做不到；pykakasi 部分代码是 GPL，与本项目 MIT 不兼容。再把词的读音和字面对齐，只给汉字部分注音（温め→温[あたた]め）。分级规则直接读 `skill/references/basic_kanji.md`（D-010），Skill 和应用共用一个数据源。 |

**这里的 NLP**：ASR（序列到序列的语音识别）+ 形态素分析（分词、读音消歧）+ 读音与字面的对齐（用假名做锚点的正则对齐）。

## D-013 按「一段话」给建议，字幕可回看（来自第一次真人测试，2026-10-24）

**背景**：作者第一次真人测试（放一段日语独白视频）的反馈：①字太大；②对方说一长段时，建议总是只针对其中一句，没有上下文；③字幕刚看清是什么字就被下一句顶掉。日志（`logs/live-20261024-225627.jsonl`，不提交）印证了这三点：8 句平均 43 字；其中一句只有「そうですね私」（换气时被切开的半句），模型单独对它回了「私もそう思います」；8 句里有 2 句模型没标 ⭐，整条建议被判为错误。

**根本原因**：D-012 的提示词写的是「只回复对方刚说的这一句」，并且每出一句字幕就请求一次。这对一问一答合适，对连续讲话不合适——分句器每停顿 0.6 s 就切一刀，「一句」常常只是半句。

| 问题 | 可选方案 | 选择与原因 |
|---|---|---|
| 什么时候请求建议 | ①每句字幕都请求（D-012）②对方停顿超过一个阈值才请求，把这期间的所有句子作为一段话 ③让模型自己判断话说完没有 | **②**。`TurnBuffer` 收集句子；对方停止说话后再安静 `turn_gap`（默认 0.8 s，加上分句的 0.6 s，相当于停顿约 1.4 s）才发请求；对方继续说，上一条建议就一直留在屏幕上。③要多一次 API 往返，还不稳定。 |
| 停顿从哪里算起 | 从字幕出来算 / 从停止说话算 | **从停止说话算**。第一次实现从「字幕出来」算，用假 API 加计时日志发现了竞态：分句器关闭一句后，这句还要约 0.25 s 识别，这段时间里「没人说话」被误判成说完了，前一句被单独发出（见 `tests/test_suggest.py` 的 `test_sentence_still_in_recognition_is_not_cut_off`）。 |
| 提示词 | — | 「对方刚说」改成可多行的「连续的一段话」，要求把半句和几行当成一段完整的话来理解，优先回应最后的问题；上文保留更早的 4 句。 |
| ⭐ 漏标 | 判为错误 / 补一个 | **补**：先按推荐理由里点名的风格，否则补丁寧——这是 Skill ⭐ 规则第 5 条本身的兜底（判断不了 → 丁寧）。日志里记 `star_inferred`，方便统计模型漏标的频率。 |
| 屏幕 | — | 字号默认 22 → 16，窗口宽 1100 → 900；字幕保留最近 5 句（`--history`）。 |

**代价**：每条建议多等约 0.8 s（一问一答场景：字幕 → 建议中位数 1.69 s → 2.43 s）。换来的是：说话途中不再频繁刷新、半句不再被单独回答。阈值可用 `--turn-gap` 调。

**验证**（`tools/e2e_suggest.py`，结果在 `tests/live_suggest/`）：
- 独白场景（新写的 3 段话、11 个片段，含一个半句「そうですね、私」）：请求次数 11 → **3**，每条建议回应的是整段话；字幕 → 建议 2.49 / 2.65 / 3.09 s。
- 一问一答场景（原来的 10 句）：之前被切成两半、前半句的建议作废的两处（お疲れ様です。／今日は…、明日ひま？／ご飯…）现在合成一段回答；10/10 在 3 秒内，中位数 2.43 s。
- 单元测试 71 个。

**仍未解决**：⭐ 偶尔不按规则（店员的问句 ⭐ かんたん、朋友邀约 ⭐ 丁寧）；独白第 2 段 3.09 s，略超 3 秒。

## D-014 讲述时用附和的陈述句；保存真实音频以便改识别（第二次真人测试，2026-10-24）

**背景**：第二次真人测试（同一段独白视频）的反馈：①「恥ずかしかった」两次都没认对；②建议全是问句，而对方在讲经历时，直接附和就够了。日志（`logs/live-20261024-232027.jsonl`）：6 条建议全部以问句结尾；识别错误有 恥ずかしかった→昔かった ×2、振り返る→振り行く、ヨーロッパ→ヨーロル、プラハ→エラハ。

|---|---|---|
| 全是问句 | ①改 Skill 的「句尾加一个反问」②只在应用的「实时字幕模式」里覆盖这条 | **②**。问句来自 SKILL.md A 模式的规则；它对「别人问一句、我答一句」合适，对「对方在讲故事」不合适。Skill 是第一阶段的成品，不在这次范围内改；在实时模式里规定：对方在讲述/分享时三条都用附和、共感的陈述句，不出现任何问句；只有对方提问或话题告一段落时才反问。是否也改 Skill，留给作者决定。 |

## D-015 识别模型改为 Whisper large-v3-turbo（第三次真人测试，2026-10-24）

## D-016 长句在最安静处切、每段前垫 0.3 秒静音；关闭按钮（第四次真人测试，2026-10-24）

**背景**：作者用 `--save-audio` 录了一段 3 分 29 秒的独白（20 段，`logs/audio/20261024-234557/`，不提交），并反馈字幕窗没有关闭键。录音暴露的问题比模型差异更大：

2. **整段编造**：第 5 段 12 秒里有完整的说话（音量正常），large-v3-turbo 却只输出「ご視聴ありがとうございました」，置信度还很高（no_speech_prob 0.00），靠阈值过滤不掉；第 1 段（片头）输出「おやすみなさい」。这是 Whisper 系列在音乐或开头不完整时编 YouTube 套话的已知问题。kotoba 对同一段能识别出内容（有错字）。
3. 由此看出 D-015 只凭 2 句就换默认模型，下结论太早：turbo 字错得少，但有整段丢失的风险。

**定位**：同一段第 5 段，去掉开头 1 秒或前面垫 1 秒静音，turbo 就能正常识别；和第 4 段连在一起识别效果最好。→ 起因是**片段以半个词开头**，也就是硬切。

| 问题 | 可选方案 | 选择与原因 |

| 到上限怎么切 | ①在上限处硬切（原做法）②往回找最安静的地方切，剩余部分接到下一段 ③提高上限 | **②**。在最后 4 秒里找 150 ms 平均音量最低处（换气），在那里结束这一段，后面的音频留给下一段，不丢不重；说话人还在说，`TurnBuffer` 的「正在说话」不中断，建议仍按一整段给出。③只会让字幕更晚出现。 |
